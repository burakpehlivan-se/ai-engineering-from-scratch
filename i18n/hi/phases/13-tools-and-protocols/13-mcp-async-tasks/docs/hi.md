# असिनक कार्य (एसईपी-1686)  लंबे समय तक चलने वाले काम के लिए अब कॉल करें, बाद में लाएं

> वास्तविक एजेंट काम मिनटों से घंटों तक लेता हैः आईसी रन, गहन शोध संश्लेषण, बैच निर्यात। समकालिक उपकरण कॉल कनेक्शन छोड़ने, समय बाहर, या UI को ब्लॉक. एसईपी-1686, जो 2025-11-25 में विलय हुआ था, एक कार्य आदिम जोड़ता हैः किसी भी अनुरोध को कार्य बनने के लिए बढ़ाया जा सकता है, और परिणाम बाद में प्राप्त किया जा सकता है या राज्य सूचनाओं के माध्यम से स्ट्रीम किया जा सकता है। ड्रिफ्ट-रिस्क नोटः कार्य 1 H2026 तक प्रयोगात्मक हैं; SDK सतह अभी भी विनिर्देश के आसपास डिजाइन की जा रही है।

**Type:** Build
**Languages:** Python (stdlib, async task state machine)
**Prerequisites:** Phase 13 · 07 (MCP server), Phase 13 · 09 (transports)
**Time:** ~75 minutes

## सीखने के लक्ष्य

- यह निर्धारित करें कि किसी उपकरण को सिंक्रोनस से कार्य-वर्धित (> 30 सेकंड सर्वर-साइड वर्क) तक कब बढ़ावा देना है।
- कार्य जीवन चक्र का पालन करें: `working`→ `input_required`→ `completed`/`failed`/`cancelled`. .
- निरंतर कार्य स्थिति ताकि दुर्घटनाओं में उड़ान में काम न खोए।
- सर्वेक्षण`tasks/status`और लाओ`tasks/result`सही कहा।

## समस्या

ए `generate_report`उपकरण एक बहु-मिनट निष्कर्षण पाइपलाइन चलाता है. समकालिक मॉडल के तहत विकल्पः

1. तीन मिनट के लिए कनेक्शन खुला रखें. दूरस्थ परिवहन इसे छोड़; ग्राहकों समय बाहर; UI फ्रीज.
2. एक स्थान धारक के साथ तुरंत वापस; ग्राहक को कस्टम अंत बिंदु पर सर्वेक्षण करने के लिए आवश्यक है। MCP एकरूपता तोड़ता है।
3. आग और भूल; कोई परिणाम नहीं।

कोई भी अच्छा नहीं है। SEP-1686 एक चौथा जोड़ता हैः कार्य वृद्धि। किसी भी अनुरोध (आमतौर पर `tools/call`) को कार्य के रूप में टैग किया जा सकता है. सर्वर तुरंत कार्य आईडी लौटाता है. ग्राहक सर्वेक्षण `tasks/status`और लाता है `tasks/result`सर्वर-साइड स्थिति पुनर्प्रारंभ से बचता है।

## अवधारणा

### कार्य बढ़ाएँ

एक अनुरोध निर्धारित करके एक कार्य बन जाता है `params._meta.task.required: true`(या `optional: true`सर्वर तुरंत प्रतिक्रिया देता हैः

```json
{
  "jsonrpc": "2.0", "id": 1,
  "result": {
    "_meta": {
      "task": {
        "id": "tsk_9f7b...",
        "state": "working",
        "ttl": 900000
      }
    }
  }
}
```

`ttl`सर्वर की स्थिति बनाए रखने का वादा है; ttl के बाद कार्य परिणाम को त्याग दिया जाता है।

### प्रति उपकरण ऑप्ट-इन

उपकरण नोटिस कार्य समर्थन घोषित कर सकते हैंः

- `taskSupport: "forbidden"` यह उपकरण हमेशा समकालिक रूप से चलता है। तेजी से उपकरणों के लिए सुरक्षित।
- `taskSupport: "optional"` ग्राहक कार्य वृद्धि का अनुरोध कर सकता है।
- `taskSupport: "required"` क्लाइंट कार्य वृद्धि का उपयोग करना चाहिए।

ए `generate_report`उपकरण होगा `required`.`notes_search`उपकरण होगा `forbidden`. .

### राज्य

```
working  -> input_required -> working  (loop via elicitation)
working  -> completed
working  -> failed
working  -> cancelled
```

राज्य मशीन केवल एक बार जोड़ने के लिए है `completed`,`failed`या `cancelled`, कार्य टर्मिनल है.

### विधि

- `tasks/status {taskId}` वर्तमान स्थिति और प्रगति संकेत देता है।
- `tasks/result {taskId}` ब्लॉक या वापस 404 यदि अभी तक नहीं किया गया है।
- `tasks/cancel {taskId}` अशक्त; टर्मिनल राज्यों को अनदेखा करना।
- `tasks/list` वैकल्पिक; सक्रिय और हाल ही में पूरा किए गए कार्यों की सूची देता है।

### स्ट्रीमिंग स्टेट में बदलाव

जब सर्वर इसे सपोर्ट करता है, तो क्लाइंट स्टेट नोटिफिकेशन को सब्सक्राइब कर सकता हैः

```
server -> notifications/tasks/updated {taskId, state, progress?}
```

सर्वेक्षण के बजाय स्ट्रीम करने वाले ग्राहकों को बेहतर अनुभव मिलता है। मतदान हमेशा न्यूनतम सतह के रूप में समर्थित होता है।

### टिकाऊ स्थिति

विनिर्देशों के लिए आवश्यक सर्वर जो कार्य समर्थन की घोषणा करते हैं, राज्य को बनाए रखने के लिए। एक क्रैश को ttl के भीतर पूरा परिणाम नहीं खोना चाहिए। भंडारण SQLite से Redis तक फ़ाइल सिस्टम तक है। पाठ 13 उपयोग फ़ाइल सिस्टम का उपयोग करता है।

### रद्द करने की अर्थशास्त्र

`tasks/cancel`यदि कार्य मध्य निष्पादन में है, तो सर्वर रुकने का प्रयास करता है (कार्यकर्ता-सहकारी रद्दता जांचें) । यदि पहले से ही टर्मिनल है, तो अनुरोध नो-ऑप है।

### दुर्घटना से पुनर्प्राप्ति

सर्वर प्रक्रिया को पुनरारंभ करने परः

1. सभी निरंतर कार्य राज्यों को लोड करें।
2. किसी को भी चिह्नित करें`working`कार्य जिनकी प्रक्रिया में मृत्यु हो गई है`failed`त्रुटि के साथ `CRASH_RECOVERY`. .
3. संरक्षित करें`completed`/`failed`/`cancelled`उनके लिए.

### असिनक्रॉन कार्य प्लस नमूनाकरण

एक कार्य स्वयं बुला सकता है`sampling/createMessage`. यह है कि लंबे समय तक चलने वाले अनुसंधान कार्यों का काम कैसे करता हैः सर्वर के कार्य थ्रेड ग्राहक के मॉडल को आवश्यकतानुसार नमूने करता है, जबकि ग्राहक के UI कार्य को प्रदर्शित करता है `working`आवधिक प्रगति अद्यतन के साथ।

### यह प्रयोगात्मक क्यों है

SEP-1686 2025-11-25 में शिप किया गया था लेकिन व्यापक रोडमैप में तीन खुले मुद्दे हैंः टिकाऊ सदस्यता आदिम, उप-कार्य (माता-पिता-बच्चा कार्य संबंध), और परिणाम-टीटीएल मानकीकरण। 2026 तक विनिर्देश विकसित होने की उम्मीद करें। उत्पादन कोड को केवल सामान्य मामले के लिए कार्यों को स्थिर माना जाना चाहिए और उप-कार्य के लिए भविष्य के एसडीके परिवर्तनों से बचना चाहिए।

## इसका प्रयोग करें

`code/main.py`एक टिकाऊ कार्य भंडार (फाइल सिस्टम द्वारा समर्थित) और एक `generate_report`ग्राहक उपकरण को कॉल, तुरंत एक कार्य आईडी प्राप्त, सर्वेक्षण `tasks/status`जबकि कार्यकर्ता प्रगति को अद्यतन करता है, और लाता है `tasks/result`जब किया गया है। रद्द काम करता है; दुर्घटना वसूली कार्यकर्ता धागा मारने और पुनः लोड स्थिति द्वारा अनुकरण किया जाता है।

क्या देखना हैः

- कार्य स्थिति JSON तक बनी रही `/tmp/lesson-13-tasks/<id>.json`. .
- कार्यकर्ता धागे अद्यतन `progress`क्षेत्र; सर्वेक्षण यह आगे बढ़ रहा है दिखाता है।
- ग्राहक पक्ष से रद्द एक घटना निर्धारित करता है; कार्यकर्ता जल्दी चेक करता है और बाहर निकलता है।
- राज्य "क्रैश" पर पुनः लोड उड़ान में कार्य को चिह्नित करता है`failed`के साथ`CRASH_RECOVERY`. .

## इसे भेजें

यह सबक हमें फल देता है`outputs/skill-task-store-designer.md`. एक लंबे समय से चल रहे उपकरण (अनुसंधान, निर्माण, निर्यात) को देखते हुए, कौशल कार्य भंडार (स्थिति आकार, ttl, स्थायित्व) डिजाइन करता है, सही कार्य चुनता हैसहायता ध्वज, और प्रगति सूचनाओं का स्केच देता है।

## व्यायाम

1. दौड़ें`code/main.py`. एक किक शुरू .`generate_report`कार्य, मतदान की स्थिति, फिर परिणाम लाओ.

2. एक जोड़ें `tasks/cancel`मध्य-चलन कॉल करें. यह सत्यापित करें कि कार्यकर्ता सम्मान करता है और राज्य बन जाता है`cancelled`. .

3. दुर्घटना पुनर्प्राप्ति का अनुकरण करेंः श्रमिक धागा को मारें, लोडर को पुनरारंभ करें, और `CRASH_RECOVERY`विफलता मोड।

4. SQLite में स्टोर का विस्तार करें. स्थायित्व जीतें समान हैं; क्वेरी विकल्प खुलते हैं (सत्र X से सभी कार्यों की सूची) ।

5. 2026 के लिए एमसीपी रोडमैप पोस्ट पढ़ें। अगले वर्ष एसडीके एपीआई डिजाइन को प्रभावित करने की संभावना वाले एक कार्य-संबंधित खुले मुद्दे की पहचान करें।

## प्रमुख शर्तें

| Term | What people say | What it actually means |
|------|----------------|------------------------|
| Task | "Long-running tool call" | Request augmented with `_meta.task` for async execution |
| SEP-1686 | "Tasks spec" | Spec Evolution Proposal that added Tasks in 2025-11-25 |
| `_meta.task` | "Task envelope" | Per-request metadata containing id, state, ttl |
| taskSupport | "Tool flag" | `forbidden` / `optional` / `required` per tool |
| `tasks/status` | "Poll method" | Fetch current state and optional progress hint |
| `tasks/result` | "Fetch result" | Returns the completed payload or 404 if not yet done |
| `tasks/cancel` | "Stop it" | Idempotent cancellation request |
| ttl | "Retention budget" | Milliseconds the server promises to keep the task state |
| `notifications/tasks/updated` | "State push" | Server-initiated state-change event |
| Durable store | "Crash-safe state" | Filesystem / SQLite / Redis persistence layer |
