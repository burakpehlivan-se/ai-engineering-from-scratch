# एमसीपी परिवहन  स्टूडियो बनाम स्ट्रीम करने योग्य HTTP बनाम एसएसई माइग्रेशन

> स्टूडियो स्थानीय रूप से और कहीं भी काम नहीं करता है। स्ट्रीम करने योग्य HTTP (2025-03-26) रिमोट मानक है। पुराना HTTP + SSE परिवहन अप्रचलित है और 2026 के मध्य में हटा दिया जाएगा। गलत परिवहन का चयन करने से एक प्रवास की लागत होती है; सही चुनने से सत्र निरंतरता और DNS-रिवाइंडिंग सुरक्षा के साथ एक दूरस्थ-होस्टेबल MCP सर्वर खरीदता है।

**Type:** Learn
**Languages:** Python (stdlib, Streamable HTTP endpoint skeleton)
**Prerequisites:** Phase 13 · 07, 08 (MCP server and client)
**Time:** ~45 minutes

## सीखने के लक्ष्य

- स्टूडियो और स्ट्रीम करने योग्य HTTP के बीच चयन करें तैनाती के आकार के आधार पर (स्थानीय बनाम रिमोट, एकल प्रक्रिया बनाम बेड़े) ।
- स्ट्रीम करने योग्य HTTP एकल-अंत बिंदु पैटर्न को लागू करेंः अनुरोधों के लिए POST, सत्र धारा के लिए GET।
- लागू करना`Origin`डीएनएस-रिफांडिंग को हराकर सत्यापन और सत्र-आईडी सेमेटिक।
- 2026 के मध्य में हटाने की समय सीमा से पहले एक पुराने HTTP + SSE सर्वर को Streamable HTTP में माइग्रेट करें।

## समस्या

पहला एमसीपी रिमोट ट्रांसपोर्ट (2024-11) HTTP+SSE थाः दो एंडपॉइंट्स, क्लाइंट के POST के लिए एक और सर्वर-सेन्ट-इवेंट्स चैनल सर्वर-टू-क्लाइंट स्ट्रीम के लिए। यह काम किया। यह भी नासमझ थाः प्रति सत्र दो एंडपॉइंट्स, कुछ सीडीएन के सामने टूटने वाले कैश, और लंबे समय तक चलने वाले एसएसई कनेक्शन पर कड़ी निर्भरता जो कुछ WAF आक्रामक रूप से समाप्त करते हैं।

2025-03-26 स्पेसिफिकेशन ने इसे स्ट्रीम करने योग्य HTTP के साथ बदल दियाः एक एंडपॉइंट, क्लाइंट अनुरोधों के लिए POST, सत्र स्ट्रीम स्थापित करने के लिए GET, दोनों साझा करते हैं `Mcp-Session-Id`हेडर. तब से निर्मित या माइग्रेट किए गए प्रत्येक सर्वर स्ट्रीम करने योग्य HTTP का उपयोग करता है। पुराने SSE मोड को अप्रचलित किया जा रहा है  एटलसियन रोवो ने इसे 30 जून, 2026 को हटा दिया; केबुला 1 अप्रैल, 2026; अधिकांश शेष उद्यम सर्वर 2026 के अंत तक।

और स्टूडियो अभी भी स्थानीय सर्वर के लिए मायने रखता है। क्लाउड डेस्कटॉप, वीएस कोड, और हर आईडीई के आकार के क्लाइंट स्टूडियो के माध्यम से सर्वर उत्पन्न करते हैं। सही मानसिक मॉडलः स्टूडियो "इस मशीन के लिए", स्ट्रीम करने योग्य HTTP "नेटवर्क पर। कोई क्रॉस-ओवर नहीं।

## अवधारणा

### स्टूडियो

- बाल-प्रक्रिया परिवहन. ग्राहक सर्वर को जन्म देता है, stdin/stdout के माध्यम से संवाद करता है.
- प्रत्येक पंक्ति के लिए एक JSON वस्तु. न्यूलाइन-सीमित.
- कोई सत्र आईडी नहीं; प्रक्रिया पहचान सत्र है।
- कोई auth आवश्यक नहीं है (बच्चा माता-पिता की विश्वास सीमा को विरासत में देता है) ।
- कभी भी दूरस्थ सर्वर के लिए उपयोग न करें  आपको सुरंग के लिए SSH या सॉकेट की आवश्यकता होगी, जिसके बाद स्ट्रीम करने योग्य HTTP का उपयोग करें।

### स्ट्रीम करने योग्य HTTP

एकल अंत बिंदु `/mcp`(या किसी भी पथ) तीन HTTP विधियों का समर्थन करता हैः

- **POST /mcp.**क्लाइंट एक JSON-RPC संदेश भेजता है। सर्वर या तो एक एकल JSON प्रतिक्रिया, या एक या अधिक प्रतिक्रियाओं की SSE धारा (बच प्रतिक्रियाओं और उस अनुरोध से संबंधित सूचनाओं के लिए उपयोगी) के साथ जवाब देता है।
- **GET /mcp.**क्लाइंट एक लंबे समय तक चलने वाले SSE चैनल खोलता है। सर्वर इसका उपयोग सर्वर-से-क्लाइंट अनुरोधों (सैंपलिंग, सूचनाएं, निष्कर्षण) के लिए करता है।
- **DELETE /mcp.**ग्राहक स्पष्ट रूप से सत्र समाप्त करता है।

सत्रों की पहचान `Mcp-Session-Id`हेडर सर्वर पहली प्रतिक्रिया पर सेट करता है और क्लाइंट प्रत्येक बाद के अनुरोध पर प्रतिध्वनित करता है। सत्र आईडी को क्रिप्टोग्राफिक रूप से यादृच्छिक होना चाहिए (128+ बिट्स); क्लाइंट द्वारा चुने गए आईडी को सुरक्षा के लिए खारिज कर दिया जाता है।

### एकल अंत बिंदु बनाम दो

पुराने स्पेसिफिकेशन से दो-एंडपॉइंट मोड अभी भी 2026 में कॉल करने योग्य है। स्पेसिफिकेशन इसे "लीगेसी संगत" घोषित करता है। लेकिन सभी नए सर्वर एकल-एंडपॉइंट होने चाहिए। आधिकारिक एसडीके एकल-एंडपॉइंट उत्सर्जन करते हैं; केवल एक अप्रवासी रिमोट से बात करते समय ही विरासत मोड का उपयोग करें।

### `Origin`सत्यापन और DNS-रिवाइंडिंग

ब्राउज़र MCP क्लाइंट नहीं हैं (आज), लेकिन एक हमलावर एक वेब पेज बना सकते हैं जो एक ब्राउज़र को POST करने के लिए आश्वस्त करता है `localhost:1234/mcp` जहां उपयोगकर्ता का स्थानीय MCP सर्वर सुनता है। यदि सर्वर चेक नहीं करता है `Origin`, ब्राउज़र की एक ही मूल नीति इसे सहेजने के लिए नहीं होगा क्योंकि `Origin: http://evil.com`क्रॉस-उत्पत्ति मान्य है।

2025-11-25 विनिर्देश सर्वर को अनुरोधों को अस्वीकार करने की आवश्यकता है जिनके `Origin`अनुमति सूची में आम तौर पर MCP क्लाइंट होस्ट (`https://claude.ai`,`vscode-webview://*`) और स्थानीय UI के लिए स्थानीय होस्ट वैरिएंट।

### सत्र आईडी जीवन चक्र

1. ग्राहक बिना `Mcp-Session-Id`. .
2. सर्वर एक यादृच्छिक आईडी, सेट आवंटित करता है `Mcp-Session-Id`प्रतिक्रिया हेडर पर।
3. ग्राहक सभी बाद के अनुरोधों पर उस हेडर की प्रतिध्वनि करता है और पर `GET /mcp`धारा के लिए.
4. सत्र सर्वर द्वारा रद्द किया जा सकता है; बाद के अनुरोधों पर क्लाइंट 404 देखता है और उसे फिर से आरंभ करना होगा।
5. ग्राहक स्पष्ट रूप से सफाई बंद करने के लिए सत्र को हटा सकता है।

### रखवाली और पुनः कनेक्ट करना

एसएसई कनेक्शन गिर जाता है. ग्राहक फिर से उसी के साथ पुनः प्राप्त करके स्थापित करता है `Mcp-Session-Id`. सर्वर को ब्रेकडाउन के दौरान याद किए गए घटनाओं को कतार में रखना चाहिए (एक उचित विंडो तक) और `last-event-id`हेडर ग्राहक प्रतिध्वनित करता है।

चरण 13 · 13 में कार्य शामिल हैं, जो पूरे सत्र के बाद भी लंबे समय तक चलने वाले काम को जीवित रहने देते हैं।

### पीछे की संगतता जांच

एक क्लाइंट जो पुराने और नए दोनों सर्वर का समर्थन करना चाहता हैः

1. `/mcp`. .
2. यदि प्रतिक्रिया है `200 OK`JSON या SSE के साथ, यह Streamable HTTP है.
3. यदि प्रतिक्रिया है `200 OK`के साथ`Content-Type: text/event-stream`और एक `Location`एक माध्यमिक अंत बिंदु की ओर इशारा करने वाले हेडर, यह विरासत HTTP + एसएसई है;  का पालन करें`Location`. .

### क्लाउडफ्लेयर, ngrok और होस्टिंग

2026 में उत्पादन रिमोट MCP सर्वर Cloudflare वर्कर्स (उनके MCP एजेंट एसडीके के साथ), वर्सेल फ़ंक्शन, या कंटेनर नोड / पायथन पर चलते हैं। कुंजीः आपकी होस्टिंग को SSE GET के लिए लंबे समय तक चलने वाले HTTP कनेक्शन का समर्थन करना चाहिए। वर्सेल की मुफ्त स्तर कैप 10 सेकंड में होती है और अनुपयुक्त है। क्लाउडफ्लेयर वर्कर्स अनिश्चित काल के स्ट्रीम का समर्थन करते हैं।

### गेटवे संरचना

जब आप गेटवे (चरण 13 · 17) के साथ कई एमसीपी सर्वरों का सामना करते हैं, तो गेटवे एक एकल स्ट्रीम करने योग्य HTTP एंडपॉइंट है जो सत्र आईडी और मल्टीप्लेक्स अपस्ट्रीम को फिर से लिखता है। गेटवे परत पर उपकरण विलय किए जाते हैं; क्लाइंट एक एकल तार्किक सर्वर देखता है।

### परिवहन विफलता मोड

- **stdio SIGPIPE.**बाल प्रक्रिया मृत्यु लेखन के बीच SIGPIPE को बढ़ाता है; सर्वर को साफ बाहर जाना चाहिए. ग्राहकों को EOF का पता लगाना चाहिए और सत्र को मृत चिह्नित करना चाहिए।
- **HTTP 502 / 504.**Cloudflare, nginx और अन्य प्रॉक्सी इन अपस्ट्रीम विफलता पर emit करते हैं. स्ट्रीम करने योग्य HTTP क्लाइंट्स को एक छोटी बैकऑफ के बाद एक बार फिर से प्रयास करना चाहिए।
- **SSE connection drop.**TCP RST, प्रॉक्सी टाइमआउट, या क्लाइंट नेटवर्क परिवर्तन धारा बंद करता है। क्लाइंट से फिर से कनेक्ट होता है `Mcp-Session-Id`और वैकल्पिक `last-event-id`फिर से शुरू करने के लिए।
- **Session revocation.**सर्वर सत्र आईडी को अमान्य करता है; क्लाइंट अगले अनुरोध पर 404 देखता है। क्लाइंट को फिर से हाथ मिलाया जाना चाहिए।
- **Clock skew.**क्लाइंट पर संसाधन-टीटीएल गणना सर्वर से भिन्न होती है। क्लाइंट को सर्वर टाइमस्टैम्प को प्रामाणिक माना जाना चाहिए।

### स्ट्रीम करने योग्य HTTP को कब बायपास करना है

कुछ उद्यम gRPC या संदेश-सूची परिवहन के पीछे MCP सर्वर तैनात करते हैं अपने स्वयं के नेटवर्क के भीतर। यह गैर-मानक है। MCP के विनिर्देशों ने औपचारिक रूप से इनकी परिभाषा नहीं की है। गेटवे आंतरिक रूप से gRPC का उपयोग करते हुए MCP क्लाइंटों को एक स्ट्रीम करने योग्य HTTP सतह का जोखिम उठा सकते हैं। बाहरी सतह विनिर्देशों के अनुरूप रखें; गेटवे अनुवाद का मालिक है।

## इसका प्रयोग करें

`code/main.py` का उपयोग करके एक न्यूनतम Streamable HTTP अंत बिंदु लागू करता है`http.server`यह पोस्ट, प्राप्त, और हटाने पर संभालता है।`/mcp`, सेट `Mcp-Session-Id`पहली प्रतिक्रिया पर, सत्यापित करता है `Origin`प्रसंस्करणकर्ता पाठ 07 नोट्स सर्वर के डिस्पैच तर्क का पुनः उपयोग करता है।

क्या देखना हैः

- POST हैंडल JSON-RPC शरीर को पढ़ता है, डिस्पैच करता है, और एक JSON प्रतिक्रिया लिखता है (एक प्रतिक्रिया संस्करण; SSE संस्करण संरचनात्मक रूप से समान है) ।
- `Origin`चेक डिफ़ॉल्ट को अस्वीकार करता है `http://evil.example`जांच लेकिन स्वीकार करता है `http://localhost`. .
- सत्र आईडी यादृच्छिक 128-बिट हेक्स स्ट्रिंग हैं; सर्वर प्रति सत्र की स्थिति को स्मृति में रखता है।

## इसे भेजें

यह सबक हमें फल देता है`outputs/skill-mcp-transport-migrator.md`. एक HTTP+SSE (वंश) MCP सर्वर को देखते हुए, कौशल सत्र-आईडी निरंतरता, मूल जांच और पीछे की ओर संगत जांच समर्थन के साथ स्ट्रीम करने योग्य HTTP के लिए एक प्रवासन योजना उत्पन्न करता है।

## व्यायाम

1. दौड़ें`code/main.py`. . एक पोस्ट`initialize`से`curl`और ध्यान दें `Mcp-Session-Id`उत्तर हेडर. एक दूसरा अनुरोध पोस्ट करें जो हेडर को प्रतिध्वनित करता है और सत्र निरंतरता की पुष्टि करता है।

2. एक GET हैंडर जो एक SSE धारा खोले जोड़ें. एक भेजें `notifications/progress`एक ही सत्र आईडी के साथ फिर से कनेक्ट करके और सर्वर इसे स्वीकार करता है की पुष्टि करें.

3. `last-event-id`पुनः कनेक्ट पर, उस आईडी के बाद से उत्पन्न किसी भी घटना को पुनः खेलें।

4. विस्तार `Origin`वाइल्डकार्ड पैटर्न का समर्थन करने के लिए सत्यापन (`https://*.example.com`) और पुष्टि करें कि यह स्वीकार करता है `https://app.example.com`लेकिन अस्वीकार करता है `https://evil.example.com.attacker.net`. .

5. आधिकारिक रजिस्ट्री से एक विरासत HTTP + SSE सर्वर लें (कई हैं) और माइग्रेशन का स्केच लेंः एंडपॉइंट हैंडलिंग, सत्र आईडी जनरेशन और हेडर सेमेटिक में क्या बदलाव हैं।

| HTTP+SSE | "Legacy" | Two-endpoint model being removed in mid-2026 |
| `Mcp-Session-Id` | "Session header" | Server-assigned random id echoed on every subsequent request |
| `Origin` allowlist | "DNS-rebinding defense" | Reject requests whose Origin is not approved |
| Single endpoint | "One URL" | `/mcp` handles POST / GET / DELETE for all session operations |
| `last-event-id` | "SSE replay" | Header used to resume a dropped stream without missing events |
| Backwards-compat probe | "Old vs new detection" | Client response-shape check that auto-selects transport |
| Long-lived HTTP | "SSE streaming" | Server pushes events for minutes or hours on one TCP connection |
| Session revocation | "Force re-init" | Server invalidates a session id; client must handshake again |
